## 已确认问题

### B1 · P1：日志块数限制不能限制连续无换行输出

位置：[AutomationRunDialog](../src/ui/automation/AutomationRunDialog.cpp)，`appendText()`，约 93 行；
[AutomationService](../src/services/automation/AutomationService.cpp)，`appendProcessOutput()`，约 555 行。

窗口只限制 5,000 个 QTextBlock 和单次 65,536 个字符。脚本反复输出短片段、不写换行时，
所有片段进入同一个块。runner 自己的 1 Mi 字符日志缓存有上限，但信号仍传递原始新片段，不能限制窗口累计内容。

最小验证对实际窗口连续调用 256 次 `appendStandardOutput(QString(4096, 'x'))`：
`contentChars=1048576, blocks=1, maximumBlocks=5000`。证明限制被绕过，没有以 OOM 作为验证手段。
显示日志或安装依赖时，持续噪声输出可能造成排版卡顿、内存增长，极端情况下进程退出并丢失未保存编辑。

建议：为窗口文档增加累计字符预算和超长单行上限；批量刷新，滚动位置由用户决定是否跟随。
runner 管进程输出缓冲，窗口管呈现预算，二者不要互相依赖。回归须包含无换行、小块持续输出及 stdout/stderr 交替输出。

### B2 · P1：合并窗口一次性解码并保留全部冲突候选图片

位置：[ProjectMergeDialog](../src/ui/project/ProjectMergeDialog.cpp)，`buildUi()` 约 76 行、
`createCandidateWidget()` 约 144 行；[ImageCanvas](../src/ui/canvas/ImageCanvas.cpp)，`setImage(path, labels)` 约 169 行。

构造窗口时遍历所有冲突，为每个候选创建画布并同步 `QImage(path)`，每个画布保留自己的 pixmap。
隐藏在堆叠页中的候选也已加载，未走主界面图片缓存。内存随全部候选图像总像素量增长，不只随当前页增长。
例如 80 个 2048×4096、32 位解码候选约为 2.5 GiB，尚未计算额外开销；这是规模估算，不是实测峰值。

建议：只创建/加载当前冲突页，切换时复用候选视图；共用图像解码与有界缓存基础设施。
合并控制器只维护来源选择，不承担解码。测试应验证大量未访问冲突不触发图片加载、切换后旧结果不覆盖当前页、关闭时安全释放。

### B3 · P2：主窗口导航快捷键截获搜索与替换输入

位置：[MainWindowShortcutController](../src/ui/MainWindowShortcutController.cpp)，`handleGlobalShortcut()` 约 56 行；
[ProjectSearchPanel](../src/ui/search/ProjectSearchPanel.cpp)，约 36、93 行。

文本输入控件只被排除出剪切/复制/粘贴/删除分支，没有被排除出标签和页面导航分支。
搜索框虽设置 `setTabChangesFocus(true)`，Tab 仍被全局过滤器消费。最小验证得到 `handled=1, nextLabel=1`。
载入仓库 `preference.json` 后，搜索框 Ctrl+Left 也得到 `handled=1, previousPage=1`，无法正常按词移动光标。

建议：快捷键路由显式区分标签编辑上下文、查找表单和其他输入控件。保留标签编辑器的高频切换语义，
不把这套语义扩散到所有 `QPlainTextEdit`；在路由层统一处理，不在搜索框加反向拦截补丁。
补全带主窗口事件过滤器的 Tab、Ctrl+Tab、Ctrl+方向键、F3 和输入法回归。

### B4 · P2：多个偏好窗口可以静默覆盖彼此的设置

位置：[MainWindow](../src/ui/MainWindow.cpp)，`openPreferences()` 约 1161 行；
[PreferenceDialog](../src/ui/preferences/PreferenceDialog.cpp)，`savePreferences()` 约 860 行。

每次打开偏好都会新建非模态窗口，各自保存当时的完整配置。窗口 A 保存后，窗口 B 仍持有旧表单，
再保存会整份覆盖 A 的结果。原子文件写入防止半文件，不解决丢失更新。
“在文本编辑器中打开”也允许在旧表单存在时外改配置，保存前没有基线比较。

建议：单主窗口只保留一个偏好窗口，再次打开时激活已有窗口；持久化层对外改配置另做版本检查。
设置草稿、dirty 与应用基线放在设置协调对象内，不复用工程文件的恢复事务或在 MainWindow 复制 JSON 合并逻辑。
回归覆盖双窗口、外部配置修改、保存失败、关闭未应用草稿。

### B5 · P2：随附配置与内置默认值造成不同的初始体验

位置：[preference.json](../preference.json)、[AppPreferences.h](../src/core/AppPreferences.h)，约 116、217 行。

| 项目 | 仓库随附配置 | C++ 内置回退值 |
| --- | --- | --- |
| 翻页 | Ctrl+Left / Ctrl+Right | Alt+Left / Alt+Right |
| 重做 | Ctrl+Shift+Z | Ctrl+Y |
| 标签表最大文本行数 | 4 | 3 |
| 自动备份检查间隔 | 200 秒 | 60 秒 |
| 气泡 / 临时编辑器不透明度 | 0.85 / 0.75 | 1.0 / 1.0 |

便携开发目录带随附 JSON，Linux 安装通常用内置值；配置缺失或损坏又会回退。
这不是存档 BUG，也可能包含有意的示例定制，但目前不应统一称为唯一“默认配置”。README 本轮已澄清两者区别。

建议：决定正式发行默认值的单一来源，另把个人/演示配置命名为示例。
构建或测试比较发布配置与内置默认值；不要在这次审查里直接覆盖用户已选择的快捷键。

### B6 · P2：恢复记录和本地审阅 JSON 缺少读取规模限制

位置：[ProjectRecoveryService](../src/services/project/ProjectRecoveryService.cpp)，`entries()` 约 84 行、
`recoverFiles()` 约 201 行；[ProjectRecoveryDialog](../src/ui/project/ProjectRecoveryDialog.cpp)，`showDetails()`；
[ReviewSessionService](../src/services/proofread/ReviewSessionService.cpp)，`loadLocal()` 约 98 行。

这些入口直接 `readAll()` 再解析 JSON，与自动化返回文件和压缩工程元数据的有界读取不同。
异常膨胀的本地记录会在恢复扫描/详情展示或打开审阅会话时占用大量内存；恢复记录还包含两份 Base64 工程快照。
本轮确认了无上限读取路径，没有做超大文件耗尽测试，也没有证明可以绕过恢复摘要校验写坏工程。

建议：由各持久化服务提供有界、检查文件类型的记录读取，限制总字节、数组项数、解码后快照规模。
恢复窗口读取服务给出的结构化详情，不再自行重复解析文件。读写上限必须成对设计，不能让合法的大工程写出自身无法恢复的日志。

## 仍需专门验证的风险

这些不是新复现的崩溃结论，不能与上面的确认问题混为一谈。

1. **共享图片的跨工程并发改名**：`ProjectFileTransaction` 按 TXT 路径上锁，两个不同 TXT 可以引用同一批图片。
   `FileRenameTransaction::apply()` 的恢复目录检查与日志创建不是一个跨工程排他步骤。
   现有项目锁不能证明共享图片改名安全；应优先补双进程交错测试，再决定目录/图片资源级协调策略。
   不应通过锁死无关工程的所有编辑来替代文件资源锁。
2. **diff-match-patch 的已知堆破坏**：上游移植问题仍未修复。`TextDiffService` 的 0.3 阈值是风险缓解，
   不是内存安全证明；低占比混合文本仍可进入 cleanup，按 QChar 遍历也不能完整统计补充平面字符。
   `catch (...)` 与重建不变量不能兜住堆破坏。保留 TODO 中的补丁、Unicode 模糊测试和 sanitizer 验收计划。
3. **外部非协作写入与断电**：最终摘要检查和原子替换之间仍有系统调用窗口；多文件改名不具备断电原子性。
   当前保留上一版本、恢复记录、失败拒绝继续写入的策略合理，但必须保留这些边界说明。
4. **图像与大工程性能**：`ImagePageCache::isCacheEntryFresh()` 在调用线程同步计算文件摘要；任务捕获/提交复核图片也有同步 IO。
   慢盘、大图、频繁翻页需要性能测量。不要以去掉摘要检查换取速度；优先调整验证调度和去重。
5. **编辑器到任务准备阶段的焦点交接**：运行状态先锁定，再调用活动编辑器提交；禁用控件可能触发焦点变化。
   本轮未证明会丢字，但完整 MainWindow 的底部/表格/临时编辑器三条路径缺少联合测试，建议补录入后立即运行/取消任务的用例。

## 全功能 UI 与操作逻辑评估

下表为产品建议，不是已实现承诺。“待验证”表示需要真机或用户测试，不能仅凭代码认定显示错误。

| 界面 / 工作流 | 现状或不合理点 | 建议表现与边界 |
| --- | --- | --- |
| 新建、打开、最近工程 | 自动恢复最近工程方便；启动失败可能缺乏明显后续入口 | 空工程状态提供打开、新建、恢复三个明确动作；常驻提示最近工程失败原因，不强制进入引导页 |
| 保存、另存、外部修改 | 版本限定覆盖与重载前备份合理，但用户要区分内存稿、磁盘稿和备份 | 冲突窗口稳定显示双方文件/时间、内存未保存状态；保留比较、另存、重载；不加入自动覆盖 |
| 主窗口布局、底栏 | 已有紧凑工具菜单和最小宽度推导，应保留；部分按钮仍为固定尺寸 | 用系统样式指标统一点击区域，验收长译文、150%/200% 缩放和窄窗口；不要新增一套布局状态 |
| 标签模式、选区模式 | 同一画布中点击行为差异很大，紧凑模式更难察觉当前模式 | 紧凑按钮/状态区保留当前模式信号，图标有可访问名称；复用原动作，不复制模式变量 |
| marker 悬停、移动、右键删除 | 右键立即删除是既有高频需求；多选时只删被点者应保持 | 删除后短提示具体序号及撤销入口，不对每次右键删除加确认；悬停仍不得劫持多选与视口焦点 |
| 标签表格与三种编辑器 | 三入口各有价值；导航键作用域有 B3 问题 | 共用提交/取消/导航契约；搜索表单独立键盘语义；保留原文本选择和输入法行为 |
| 分组创建、删除、插入、筛选 | 插入分组和显示筛选是两种不同状态；查找定位会主动放开目标分组筛选 | 短提示筛选发生变化；筛选为空提供清除筛选入口；删除组仍明确标签迁移目标和数量 |
| 全文查找 | 多条件堆在单条横向布局；查询为同步扫描；运行自动化时有结果但 `navigate()` 直接返回 | 窄屏把次要筛选折叠；区分可导航与可编辑能力，允许只读定位或明确禁用理由；大工程异步化前先测量 |
| 替换预览 | 每个命中一行，却展示整个标签的最终文本，同一标签多次命中看起来像重复操作 | 按标签分组显示完整前后文本，命中子项只显示局部上下文和高亮；提供全选/清空；仍整批提交一次撤销 |
| 页面管理 | 四列已经区分当前、待应用、输入预览；“Rename Images” 区域还同时负责缺失来源修复 | 区域改用覆盖两种操作的名称；行内明确“磁盘改名”或“修改引用”；固定显示草稿待处理总数 |
| 页面管理确认 / 取消 | 输入未加入草稿就点确定，当前输入不会提交；筛选只影响显示、提交覆盖完整草稿 | 不自动应用未加入的输入；离开前提示有未加入的有效候选，允许返回。确认区分改名、引用、移除、重排数量和撤销后果 |

## 代码组织与实施顺序

整体已形成有价值的边界：稳定 ID/版本和任务提交在服务层，页面管理有独立草稿，
标签变更共用编辑控制器，模型不长期持有项目容器内部地址。没有证据支持推倒这些结构。
更值得处理的是少数跨界重复和缺失契约：

1. **资源预算与图片显示复用**：先解决 B1/B2。日志预算不依赖文本块；合并、校对预览复用图片读取设施。
   后续评估按解码字节计量缓存，避免仅按“页数”推算大图内存。
2. **输入作用域与操作能力**：快捷键分发识别工作区语境；只读浏览和修改权限分开。
   复用 `EditorStateController` / `LabelSelectionController`，不要再增加来源布尔值组合和相互补偿的事件过滤器。
3. **设置持久化**：单窗口草稿与配置版本校验独立于工程存档；发布默认配置建立单一来源。
4. **文件工作流边界**：HTML 临时文件转最终文件仍在 `ProofreadChangesDialog.cpp` 中自行复制；
   恢复窗口仍解析 JSON。逐步移到相应 IO/持久化服务，UI 只协调进度和用户决定。
   共用机制时保留不同策略：恢复副本不得覆盖、HTML 可经用户确认覆盖、工程写入需版本与恢复保护。
5. **有界输入与竞争测试**：处理 B6；对共享图片跨工程改名补双进程测试后决定资源锁粒度。
   外部 Python 进程继续只提交值结果，不能以便利为由直接读写活动 Project。

不建议为了本轮建议引入插件总线、全局状态机框架或通用“万能控制器”。
每次改动按相应职责提交，先补失败用例，再改实现；优化不应削弱当前摘要、恢复日志和撤销保护。
