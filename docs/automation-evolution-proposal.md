# 自动化功能演进分析

日期：2026-09-06。状态：演进设计；[身份、版本与任务提交底座](automation-foundation.md) 已实现，
原生 v2 批处理 SDK 已实现，当前接口以 [开发指南](automation-scripting.md) 为准。
原生候选审核、可复用 worker 和双向 IPC 仍为后续工作。

面向用户自行开发扩展的接口、Python SDK、清单、版本兼容与开发工具链，进一步设计见 [自动化扩展 API 与 SDK](automation-extension-sdk-design.md)。

第二轮不受现有实现限制的决策见 [API 边界、Python 运行位置与工程访问模型](automation-api-boundaries.md)：推荐可复用外部 worker、持续通信、显式新快照与受控短事务。后续章节保留产品演进建议，不以旧脚本能力作为新接口上限。

## 1. 结论

建议采用 **原生工作流 + 统一变更草稿 + 可替换计算后端**，而不是在“外部 Python 脚本”和“全部写进 C++”之间二选一。

- 用户直接使用“识别文字”“翻译所选标签”“批量处理”，无需理解脚本、JSON 和配置脚本。
- 普通文本处理由 C++ 完成；常用在线翻译可由原生 HTTP 后端完成，不依赖 Python。
- 本地 OCR 等模型能力继续在独立工作进程中运行，按需启动并复用模型。Python 是一种后端实现，不再决定产品界面。
- 所有修改先形成可验证提案，由主程序批准策略与统一编辑入口提交；AI/大范围结果使用候选审核，用户已授权的窄范围宏可免二次弹窗。后端不直接改工程文件或 Qt 对象。
- 不维护 v1 兼容入口。新脚本直接使用稳定 ID、作用域和统一提交服务；旧 SDK/API 已删除。

最值得先做的不是更换通信格式，而是让 **预览的结果能直接编辑、勾选和应用，不必再运行一次算法**。

## 2. 当前实现与剩余边界

当前链路为清单范围 → 宿主任务快照 → 独立 Python → v2 LabelChange → 依赖校验 → 统一撤销。
旧 SDK、页名/行号转换与 OCR/翻译脚本已移除；具体线上格式见
[开发指南](automation-scripting.md)，宿主版本规则见 [基础契约](automation-foundation.md)。

已解决错误字段静默应用、长期行号寻址、整工程快照适配和独立撤销路径。
仍待解决的产品问题是：原生候选审核、OCR/翻译提供者、模型生命周期、细粒度重试、
素材固定、按依赖放开交互，以及只读原文与候选的长期数据模型。
下面是这些后续工作的方案，不是本分支已开放能力的清单。

## 3. 可选实现路线

以下适配度是结合本项目作出的工程判断，不是对技术方案的通用排名。

| 路线 | 优点 | 代价/边界 | 建议 |
| --- | --- | --- | --- |
| 继续文件交换，补齐原生预览与草稿 | 隔离已有，新 v2 批处理已接入 | 没有实时分项结果，模型启动开销仍在 | 作为第一步完全可行 |
| 独立常驻工作进程 + 双向消息 | 模型复用、结构化进度、分项候选，主程序不加载模型库 | 需要协议、取消、重启和资源回收 | 本地 OCR 的推荐路线 |
| C++ 原生 HTTP 翻译 | 无需 Python；配置、网络错误和结果审核统一 | 增加网络/TLS 部署、不同服务协议适配 | 常用在线翻译推荐 |
| 嵌入 CPython/绑定 C++ 对象 | 脚本调用看起来直接，易接 Python 算法 | 解释器与扩展库部署、线程与对象生命周期复杂；原生扩展崩溃可影响主进程 | 不建议作为本次主线 |
| Qt/C++ 动态插件 | 能扩展原生能力 | ABI、编译器/Qt 版本、静态发行兼容及崩溃隔离代价 | 暂不面向普通脚本作者开放 |
| 内嵌 JS/Lua 宏 | 小型规则处理表达方便 | OCR/翻译仍需后端，还新增语言与安全边界 | 有真实宏需求后再评估 |
| 独立 HTTP 服务 | 适合已有模型服务器、跨语言和远端 GPU | 服务部署、认证、端口和敏感数据外传管理 | 可选后端，不要求所有用户部署 |

Python 官方提供嵌入接口，但嵌入本身不提供 LabelQt 的工程一致性与撤销语义。[Python 嵌入文档](https://docs.python.org/3/extending/embedding.html)

Qt 支持应用插件接口；这并不意味着任意插件都能跨构建环境复用。[Qt 插件文档](https://doc.qt.io/qt-6/plugins-howto.html)

因此，不建议为了得到 `project.labels[0].text = ...` 这样的表面便利，把活动工程、窗口指针和可写容器暴露给外部算法。

## 4. 推荐结构与职责

下面是建议的逻辑边界，不要求一次性创建同名类，也不建立通用插件框架后才实现用户功能。

```text
识别/翻译/批处理界面
          |
任务协调：范围、快照、状态、取消、候选草稿
          |
计算后端：原生文本规则 | HTTP 翻译 | 本地模型进程 | 旧脚本适配器
          |
类型化候选结果 -> 校验/编辑/勾选 -> 标签变更计划
          |
LabelEditController / 共用批量编辑服务 -> UndoStack
```

| 边界 | 负责 | 不负责 |
| --- | --- | --- |
| 任务协调服务 | 生命周期、快照、范围、并发额度、超时、重试及取消 | 控件布局、模型内部算法、直接写 TXT |
| 计算后端 | 对给定输入产生 OCR/翻译/检查结果 | 工程保存、撤销、选择同步、弹宿主 UI |
| 自动化草稿 | 候选、用户修改、排除项、来源、输入版本 | 擅自回写真实工程 |
| 协议/进程适配器 | 消息编码、边界检查、传输、进程退出 | 阅读顺序、翻译风格、是否覆盖某条人工修改 |
| UI 控制器与模型 | 选择范围、展示状态、编辑候选、请求提交 | 网络调用、线程管理、JSON 业务解析 |
| 标签编辑层 | 校验提交目标、统一变更与撤销、刷新通知 | 调用模型、下载依赖、处理密钥 |

关键复用点：

- 已将原 `MainWindow::applyAutomationOperations` 的业务提交迁入标签编辑层；后续 profile 规划继续使用这条入口，不恢复独立的标签写入与撤销逻辑。
- 与 `LabelEditController::replaceTexts` 共享旧值校验和批量编辑基础。查询结果指纹如要成为通用依赖，应提取到工程版本服务，不让 OCR 依赖“全文搜索服务”。
- 复用 `TextDiffService` 显示候选译文差异，但不要把自动化候选硬塞进 `ProofreadChangesDialog`。两者的目标身份、阶段及提交含义不同。
- 复用分组筛选、表格列宽、编辑器提交、选择同步和图片解码设施；复用能力，不复用另一个窗口的整套状态。
- 任务中裁图属于图像输入服务；`ImagePageViewController` 继续协调可见页加载，不变成模型素材管理器。后端不能从 QWidget 截屏获取原图。

## 5. 用户侧应如何表现

### 5.1 OCR：先得到可检查的文字区域

入口：“自动化 → 识别文字”，也可从图像选区的上下文入口进入。界面明确范围为选区、当前页或指定页面；零选中不得悄悄变为全工程。

1. 选择后端与目标分组，范围带入当前上下文。
2. 边识别边展示完成页数及候选；原图上叠加候选框，旁边表格显示文字、阅读顺序、可用的置信信息及异常。
3. 用户可以排除误识别块、修改文字、调整阅读顺序，再应用勾选项生成标签。
4. 已有标签默认保留；“新增标签”和“更新选中标签的文本”是不同动作，不能靠距离接近就静默覆盖。

检测、识别、文字块合并、顺序判断分别返回结构化数据。后端可给出建议合并与排序；宿主提供统一审核表现，不把具体模型的所有后处理都重写成 C++。

OCR 框不是 marker：建议保留归一化多边形/区域、裁图到原图的变换、输入图像摘要和阅读顺序。最终 marker 由宿主按明确规则生成。原图旋转、EXIF 方向和选区裁剪必须使用同一坐标约定。

置信度允许缺失，并注明是检测还是识别置信度；不能把未提供置信度的模型结果包装成“100% 正确”。现有 manga-ocr 适合日文漫画识别，但具体检测和布局仍需组合能力。[manga-ocr 项目说明](https://github.com/kha-white/manga-ocr)

### 5.2 翻译：同一次候选从预览走到应用

入口：“翻译所选标签”，以及显式的当前页/页区间翻译。

- 面板使用“原文 / 候选译文 / 状态”，可编辑译文、勾选应用、仅重试失败项或重译选中项。
- 同一候选直接应用，不重新请求接口。重新生成时保留之前候选，用户已手工编辑的候选不能被流式结果覆盖。
- 支持目标语言、后端/模型、术语表和上下文范围。初版先支持一种明确验证过的接口，不宣称所有“兼容”服务完全等价。
- 跨页上下文按页/场景分批并带有限邻近上下文，不能把任意大的页区间一次塞入请求。只把本批目标返回值变成候选，上下文标签不能被顺手修改。
- 每项绑定宿主分配的不可混淆目标句柄；检查遗漏、重复、未知目标和格式错误，不按模型返回数组顺序猜位置。
- 用量与费用只展示服务真实返回的数据或明确标注的估算；超时后重试可能重复计费，取消不能保证远端停止处理。

主界面可以采用一个可收起的自动化任务面板，结果多时打开专门审核窗口。查找面板和自动化面板共享右侧工具区域的空间管理，避免两个面板同时挤压标签列表；各自服务和状态仍独立。

### 5.3 自动处理：区分文字处理与图像改写

标点统一、空白整理、术语替换、空译检查、疑似漏译等，优先使用确定性的本地规则。单条查找替换继续走现有功能，只有多规则或多阶段处理才需要批处理预设。

初版预设是一条简单顺序流程，例如“识别 → 人工确认原文 → 翻译 → 术语检查 → 应用”，不做节点连线编辑器。识别后的草稿可直接作为下一阶段输入，无需先污染真实工程；中间候选使用草稿内临时身份，在最终提交时再映射成真实标签。

如果“自动处理”包含抹字、修图或回填文字，这是图像编辑/输出领域，不是多加一个 `operations` 类型就能安全完成。建议只生成新目录中的派生文件，通过独立导出计划校验路径和覆盖策略；不得默认改写原图，也不把磁盘图像写入假装成普通文本撤销。

## 6. 原文、候选与工程格式

不建议马上把 Label 改成完整多语文档模型，但不能继续只靠覆盖 `text` 承载翻译工作流。

建议分两层：

- **任务候选层**：在本机任务目录保存输入原文、OCR 区域、译文候选、用户编辑和执行状态。使用版本化、原子保存，有容量与清理策略；不能放在脚本安装目录。
- **已应用来源层**：应用后，将必要的原文与来源关联写入统一 `LabelQtMetadata` 的版本化 section（建议名 `automationProvenance`）。正文仍是唯一的实际编辑/导出文本。密钥、整张图片、日志和模型响应全文不进入工程 metadata。

不要把来源层混入校对基线或 `reviewSession`：校对记录是比较双方差异的状态，不是翻译原文数据库。原文与候选的共享/导出应明确提示，用户可能不希望发出的译稿附带模型输入。

身份设计与旧工程迁移应区分：

1. 从零设计时将稳定 page/label/group ID、会话 epoch、单调 revision 与版本化快照纳入底座；重排/改名不使对象身份消失，撤销/重做仍增加版本。
2. 迁移旧工程须覆盖解析、身份补全、合并去重、复制生成新 ID、撤销恢复旧 ID、软删除、另存及 metadata 清理。临时兼容适配器可用会话内快照映射，结构变化后拒绝旧结果；这不是新 API 的长期边界。
3. 内容摘要用来验证“对象是否改变”，不能冒充对象 ID；两条相同文字、相同坐标的标签仍可能是不同对象。重载不保留任务句柄的有效性，不能只比较工程文件路径。

如果第一版包含持久原文关联，就必须连同稳定身份和旧工程迁移一起交付；不能先按表格行号持久化，留给以后补救。持久身份本身不意味着重启后可跳过会话/授权与内容验证。

## 7. 提交、取消与既有功能联动

### 7.1 只读执行、受控提交

每次算法读取不可变快照；持续会话可以显式取得新版本并提交阶段提案，但不能直接执行任意工程命令或原地修改共享对象。读快照、候选发布和请求宿主应用是不同能力。

提交前先通过 `EditorStateController` 提交活动文本框，再重新验证工程会话、目标身份、旧文本/分组/坐标、图片版本及任务范围。整批规划成功后，由统一标签编辑入口提交，一次用户确认对应一条主工程撤销记录。流式输出不能逐字写入正文和撤销栈。

初版可保守地使用整份相关快照校验；后续再将冲突细化到每个目标，允许用户明确排除冲突项。必须区分目标写入前提与翻译所依赖的上下文：邻近上下文变化未必写错对象，但应提示候选可能过期。

未知操作、缺失字段、非有限坐标、超大结果、越界引用、同字段重复写入都要有确定的校验结果。合法的空译文必须由显式字符串表示。默认拒绝有错误的提交集合，不静默跳过后宣称全部成功。

### 7.2 后台工作不等于随时可写

建议任务状态：准备中、运行中、等待审核、部分失败、已取消、已失败、已应用。后端完成和工程应用是两个不同结果。

- 新架构把版本验证作为允许边计算边编辑的基础，不以长期锁住用户编辑作为正常模型。旧系统迁移期间可以保留限制，不能未经版本校验就直接解除。
- 文本编辑与其他任务结果互不覆盖；页序、改名、合并等按稳定 ID 和实际读依赖验证，重载、恢复、关闭或授权撤销使旧会话失效。不能仅比较文件路径或显示序号。
- 校对模式下应用自动化仍是普通标签编辑，遵守软删除、基线和选择同步规则，不重置用户基线；变化后的旧审阅状态按既有指纹机制失效。
- 用户在另一页浏览时，后台完成只更新任务状态。应用结果默认不抢焦点、不缩放、不把画布跳回任务起点。
- 关闭工程/程序时明确处理未应用草稿。后台任务不能通过捕获旧 `Project&` 或 QWidget 指针在重载后写回。

取消请求先尝试协作停止，限时后终止工作进程。模型库若创建子进程，还需平台对应的进程树管理，不能把 `QProcess::kill()` 当成全部后代均被终止的保证。已收到的完整候选可以保留待审，但取消后到达的结果不能自动应用。

进度、候选、最终状态和工程提交分别带 task ID、请求 ID 和代次；重复消息不能重复新增标签。多任务初版按后端串行计算，统一串行提交；出现真实需求后再扩充并发队列。

## 8. 如何保留 Python 而让交互自然

### 8.1 先升级契约，再升级传输

一次性 input/output 文件现用于原生 v2 批处理，不承担旧脚本兼容；后续增加持续通信而非重新开放旧 API。
未来候选协议应支持逐项错误，但当前批处理仍为整批成功或整批拒绝。

新设计推荐按需启动、可复用的 worker：由宿主 `QProcess` 管理，通过标准输入/输出交换小型 JSON-RPC 2.0 消息，不默认开放 TCP 端口。Qt 本身支持对子进程 stdin/stdout 读写，因此双向交互并不要求嵌入解释器。[QProcess 文档](https://doc.qt.io/qt-6/qprocess.html)

可以定义 `initialize`、`task.start`、`task.progress`、`task.candidate`、`task.cancel` 等应用方法。JSON-RPC 提供请求、响应、通知和错误结构，但不定义传输分帧、任务状态、取消或权限；这些必须写入 LabelQt 自己的版本化协议，不能认为选了 JSON-RPC 就已经解决。[JSON-RPC 2.0 规范](https://www.jsonrpc.org/specification)

具体约束建议：

- 首版使用有长度上限的 UTF-8 单行 JSON 帧，并正确处理分片、粘包、非法消息、背压、事件顺序和最终结束状态。
- stdout 专用于协议、stderr 用于诊断。模型库的原生输出也可能写 stdout，需处理文件描述符层的日志重定向，不能只替换 Python `print`。无法约束的后端再使用专用 IPC 通道。
- 图像通过宿主管理的临时素材句柄交换，校验路径、尺寸、摘要、存活期和坐标变换；不在每条消息中传整页 base64，也不暴露所有工程文件路径作为默认权限。
- worker 按模型/设备配置复用实例，支持空闲释放与崩溃后重新启动。复用不意味着无限保留显存或把所有模型装进一个巨型进程。
- 允许在已有授权内取得新快照、订阅有界提交事件和请求宿主应用提案；持续交互不等于共享可写工程对象。Observer 默认只产生诊断，结构/文件操作经对应领域工作流，不提供任意反射/执行宿主函数。

### 8.2 环境管理也属于体验

不应每次 OCR 都先执行一次 `pip install -r`，也不能默认改用户系统 Python。提供“后端状态/安装/诊断”：解释器、环境、模型版本、设备、自检结果及下载大小在同一处管理。

模型后端使用用户目录里的独立环境，按后端及受支持依赖版本管理；更新先构建新环境并自检，再切换，旧环境可回退。离线安装包是可选交付物，不让主程序启动依赖在线安装成功。Python `venv` 支持独立包环境，但不包含独立下载的 Python 解释器，也不是安全沙箱。[venv 文档](https://docs.python.org/3/library/venv.html)

Windows 静态版“无需 Qt DLL”不等于“所有 OCR 能力都能装进一个小 EXE”。主程序可保持独立发行，模型与运行环境按需安装；下载来源、文件校验、模型权重许可证和磁盘空间需单独审查。

## 9. 原生 HTTP 翻译的价值与成本

现有翻译脚本主要是上下文组装、HTTP 调用和 JSON 校验，这部分可以迁入 C++ 服务，而不需要在主进程加载 AI 模型。

建议用异步 `QNetworkAccessManager` 实现一个经过验证的翻译后端；逐步增加超时、取消、限流、分批、重试和可选流式候选。界面层不直接调用网络。原生网络 API 能承接 HTTP 请求，但翻译上下文和服务响应校验仍是应用职责。[QNetworkAccessManager 文档](https://doc.qt.io/qt-6/qnetworkaccessmanager.html)

当前程序没有直接链接 `Qt6::Network`。采用此方案需要更新 CMake、Windows dynamic/static 部署、RPM 依赖与 TLS 自检。Qt Network 提供 LGPLv3 许可路径，并可能使用 OpenSSL 等依赖，必须按实际构建核对许可证与静态再链接材料，不能只加一个链接目标就算完成发行验证。[Qt Network 许可与依赖说明](https://doc.qt.io/qt-6/qtnetwork-index.html#licenses-and-attributions)

自定义 API 地址必须绑定相应密钥配置。地址/提供商切换或跨站重定向不能把原服务密钥顺带发到另一主机；远程默认 HTTPS，本机 HTTP 例外应明确。新提供商不因接口路径相似就自动继承凭据。

## 10. 安全和隐私边界

- 外部进程提供崩溃隔离，**不是安全沙箱**。当前自定义 Python 仍以用户身份运行，可以自行访问文件或网络；协议声明的权限无法阻止恶意脚本绕过宿主。
- 普通用户使用受管理的官方后端；安装自定义脚本时明确说明代码执行风险。真正运行不可信插件需要操作系统级隔离，不能靠 JSON 白名单宣传“安全”。
- 任务范围最小化。默认只发送选中正文及用户同意的上下文；发送图像、额外页面、术语表或来源文本前，展示目的地与数据类型。
- 继续通过 `SecretStore`/QtKeychain 保存密钥。原生网络后端不向子进程传密钥；确需联网的 worker 才获得该提供商的必要凭据，且不写磁盘快照、任务日志或命令行。
- 清理响应正文中的敏感信息后再记诊断；任务目录里的正文和候选也属于私有稿件，需要可见的保留/删除策略。
- 模型输入/输出都是数据，不允许模型返回的“建议”成为 shell 命令、文件路径写入授权或任意工程操作。任务范围和操作集合只能由宿主与用户决定。
- 若以后接 Agent/MCP 等外部控制入口，也只能复用同一快照/候选/提交契约；不另开绕过确认、撤销和版本校验的写入口。它不是首版 OCR/翻译体验的前置条件。

## 11. 推荐实施顺序与验收

| 阶段 | 具体交付 | 完成标准 |
| --- | --- | --- |
| A：统一候选与提交 | 稳定身份/版本、严格结果结构、自动化草稿、批准策略、统一标签编辑入口、v1 兼容适配 | 预览后应用零额外模型请求；无效字段不清空正文；一批一次撤销；过期结果拒绝写回 |
| B：原生翻译体验 | 一个 HTTP 翻译后端、配置与密钥管理、明确范围、逐项错误与重试 | 不装 Python 也可翻译；未知/重复目标被拒绝；取消与重试不覆盖已编辑候选 |
| C：本地 OCR 后端 | 独立环境、按需 worker、模型复用、区域候选审核 | 同一模型连续多页不重复初始化；崩溃不带倒主程序；裁图坐标正确；误识别可排除 |
| D：持续会话与持久上下文 | 基于已有身份/版本开放新快照、事件订阅、阶段提交、原文来源及可恢复候选 | 编辑/删除/重排/另存/合并后不错误应用；重载后验证会话与授权；上下文失效有提示 |
| E：顺序工作流 | OCR 草稿接翻译、术语检查、预设 | 中间结果不必先写入工程；部分失败可重试；没有隐式改写原图 |

阶段 A 可以先保留外部脚本，不必等待 B/C；B/C 共享契约但各自实现一种真实后端，避免提前扩展出多层注册器、总线和通用可视化流程框架。若优先需求是离线 OCR，可在 A 后先做 C。

建议回归用例包括：

- 中文、日文、emoji、换行、空字符串与重复标签的目标定位。
- 提交前修改正文、分组、marker、页序、图片引用，以及切换工程/恢复备份。
- 修订模式下批量新增/修改/删除的一次撤销与重做，未受影响页不重新加载图像、不抢焦点。
- 缺字段、未知协议版本、错误目标、非有限坐标、超长响应、重复/乱序/迟到事件和子进程崩溃。
- 一部分页面成功、一部分失败；取消后保留完整候选但不自动应用；仅重试失败项。
- OCR EXIF 方向、选区映射、缺失图片、外部图片变更及两页内容完全相同。
- 服务限流、网络断开、请求超时、跨域重定向及密钥不进入日志/快照。
- 用假后端和本地测试服务运行常规 CI；真实模型性能、显存与网络服务效果单独验收，不让自动测试依赖付费 API。

最终目标是：用户感受到的是一个有审核、有撤销、可恢复的漫画文字处理工具；Python、HTTP 或本地推理只是可替换的计算方式。
