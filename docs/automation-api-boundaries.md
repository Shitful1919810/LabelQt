# 自动化 API 边界、Python 运行位置与工程访问模型

日期：2026-09-06。状态：第二轮决策稿；[身份、版本与任务提交底座](automation-foundation.md) 已实现，
原生 v2 批处理 SDK 见 [开发指南](automation-scripting.md)；本文的持续通信、任务审核和领域工作流仍为后续设计。

本稿不以旧脚本或现有 C++ 类为架构约束。它补充并修订 [总体方案](automation-evolution-proposal.md) 与 [扩展 SDK 设计](automation-extension-sdk-design.md)：先确定理想的公开契约，再考虑迁移，而不是把当前能做的事情直接定义成最终 API 上限。

## 1. 直接回答三个问题

**该开放哪些 API？** 开放完整的领域能力，不开放任意内存和文件写入。读取、素材、计算结果、标签/分组/页序事务、领域工作流、受控交互和扩展配置应各有明确接口。权限、数据完整性校验与用户批准是三个独立条件，不能用其中一个代替其他两个。

**外部还是内嵌 Python？** 默认采用宿主管理的独立工作进程，按扩展/依赖环境与授权边界隔离、按需复用。不是每次都临时调用系统 Python。内嵌解释器不作为用户扩展的主方案；它更适合严格控制依赖的可信内置脚本或经过测量证明需要紧密调用的特定功能。

**一次性快照还是持续访问？** 不二选一。推荐 **持续通信 + 显式版本化快照 + 有边界的事务提交**。脚本可以在同一会话内多次读取新的工程状态、接收变更通知、分阶段生成结果并请求应用，但不能在另一线程/进程直接改活动工程对象，也不能把每次属性赋值都变成隐式在线写入。

一句话：**长期存活的是连接和计算资源；读取的是确定版本；写入的是用户授权、宿主验证的短事务。**

### 相比上一轮的实质调整

- 不再将“禁止直接实时对象访问”等同于“禁止获取新快照或订阅工程事件”。
- 不把五类标签操作当成最终完备接口，补齐分组、排序、领域工作流、诊断与安全交互。
- 从零设计时，把稳定身份与单调版本放在底座第一阶段，而不是先普遍锁住编辑再补版本管理。
- 不要求每个低风险宏都弹一次候选审核窗；批准强度由用户动作和副作用决定，不由插件自报“可信/确定性”决定。
- 分阶段应用可以支持，但必须是用户可见的独立提交单元；取消不是将已提交内容自动回滚。

## 2. 先区分四个正交选择

| 维度 | 选择 | 不应该混淆的事情 |
| --- | --- | --- |
| 运行位置 | 主进程 / 独立进程 | 外部进程也能高频双向通信 |
| 生命周期 | 单次启动 / 会话复用 / 常驻服务 | 内嵌不一定持续交互，外部不一定一次性 |
| 读取语义 | 固定快照 / 按需新快照 / 任意实时对象 | IPC 或线程队列都不能自行保证多次读的一致性 |
| 写入语义 | 候选草稿 / 显式事务 / 原地属性写入 | JSON-RPC、Python 绑定、锁和 GIL 都不能代替事务 |

“把 Python 嵌进去，通过线程通信访问工程”仅选定了运行位置和传输，还没有回答失效目标、半批修改、撤销、用户并发输入和插件取消的问题。反过来，外部进程也可以表现得像 SDK 中普通的异步方法调用。

## 3. Python 运行位置的取舍

| 考量 | 独立工作进程 | 主进程内嵌解释器 |
| --- | --- | --- |
| 算法原生库崩溃 | 通常限制在 worker，宿主保留候选和任务诊断 | 可直接终止主程序，影响未保存稿件 |
| 超时、死循环、无法协作取消 | 可终止并重建 worker；子进程树要另管 | 不能任意强杀解释器线程并保证宿主继续安全运行 |
| 模型复用 | worker 复用即可，不需每页重建 | 可复用，但不是独有优势 |
| 依赖冲突 | 可为不同扩展配置不同 Python/依赖环境 | 解释器版本、原生扩展、全局状态与宿主更紧密耦合 |
| 数据交换 | 需要消息与素材传输，可批量、缓存 | 直接调用成本可低，但仍需版本/所有权边界 |
| 内存与启动 | 多进程有额外开销，需要空闲释放 | 可能更省进程开销，模型内存并不会消失 |
| 打包与升级 | 主程序与解释器/模型可分开维护 | 需管理宿主 ABI、解释器链接、扩展导入及退出顺序 |
| 恶意代码 | 同用户权限并非沙箱，仍需明确代码信任 | 也不是沙箱，且与宿主共享地址空间 |

这些是本产品的架构判断，不是性能实测结论。漫画 OCR/翻译主要处理页图、文本批次和模型/网络调用，首先应测模型初始化、传图与计算耗时，而不是预设 Python-C++ 函数边界是瓶颈。

### 3.1 内嵌的真实优势和适用条件

内嵌不是错误技术：如果产品要求大量可信脚本与内部算法细粒度交互、部署环境统一、库兼容性可控，且测量证明消息/复制开销明显，可以考虑。但仍应暴露相同的快照/事务服务，不因为同进程就返回可写内部容器。Python 官方嵌入接口本身也需要负责初始化、对象转换与引用生命周期。[Python 嵌入文档](https://docs.python.org/3/extending/embedding.html)

本产品要承载用户自行安装的 OCR、模型库与网络适配器，依赖多样性和故障恢复收益更重要，因此不满足默认内嵌的优先条件。用一个单独 helper 嵌入 Python 也可以，但对 LabelQt 主程序而言，它仍是本方案的进程外 worker。

### 3.2 线程、GIL 和子解释器不是保护工程的捷径

GIL 主要约束 Python 对象访问，不保护 C++ 的工程模型，也不使 Qt 控件成为线程安全对象。free-threaded 构建改变解释器并发条件，仍不解决领域一致性与宿主线程归属。[Python 线程状态与 GIL](https://docs.python.org/3/c-api/threads.html)

Qt 的 GUI 类应在主线程使用，跨线程调用应遵守对象所属线程与事件投递规则。即使嵌入 Python，也应通过宿主队列请求服务，而不是在 Python 工作线程直接访问窗口、模型或其子对象。[Qt 线程与 QObject](https://doc.qt.io/qt-6/threads-qobject.html)

子解释器提供逻辑隔离，但同进程内不能成为严格安全隔离；第三方扩展对多解释器的兼容性也不能假定。它不替代进程故障边界。[Python 多解释器说明](https://docs.python.org/3/library/concurrent.interpreters.html)

### 3.3 推荐进程策略

- 启用后按需启动受管 worker；普通命令完成后可短时复用，模型后端按空闲策略释放。
- 扩展版本、Python 环境、模型配置和授权边界不一致时不共享进程，避免密钥或模型状态串用。
- 一个 worker 内初版串行运行算法任务，但控制通道继续处理取消与宿主响应；宿主可管理有限数量的 worker。
- 依赖加载、自检与模型下载不在 GUI 线程进行；资源配额、下载许可和失败诊断可见。
- SDK 封装 stdio/专用 IPC，普通作者不碰协议流。QProcess 已支持对子进程双向读写，不要求开放网络端口。[QProcess 文档](https://doc.qt.io/qt-6/qprocess.html)

## 4. 完备性如何定义

完备不意味着任意 C++ 方法都能从 Python 调用，而是目标用户的工作可以通过有限、可组合的领域操作完成。

| 需求 | 所需能力 | 不需要暴露 |
| --- | --- | --- |
| OCR 后生成标签 | 图像/裁图、区域结果、目标分组、标签新增提案 | 原图可写句柄、QGraphicsItem |
| 翻译选中标签并保留原文 | 目标快照、上下文、译文候选、来源记录 | 直接替换整个 Project、私有 comment 编解码 |
| 批量清理文本、移动 marker | 文本/坐标事务、错误诊断 | 任意对象 setter |
| 自动分组、建立新分组 | 分组新增、改名、重排、迁移后移除事务 | 直接操作分组 QStringList |
| 按阅读顺序整理标签 | 明确作用集及锚点的排序事务 | 可见行号、table model 的拖放函数 |
| 发现漏译、异常文本 | 只读快照、可定位诊断、可选修正提案 | 任意修改审阅状态 |
| 修复缺失图片、批量改名 | 领域规划请求与宿主确认执行 | 任意 filesystem rename/delete |
| 图片抹字/派生输出 | 标准素材、派生文件上传、用户选定导出目标 | 覆盖原图的通用写 API |
| 编辑后自动检查 | 有界事件订阅、新快照、诊断替换 | 每个键盘/鼠标事件、自动反复改正文 |
| 多步骤半自动工具 | 分阶段草稿、用户交互请求、提交回执、新快照 | 持续持有工程写锁 |
| 保存/导出当前结果 | 受控工作流请求与实际结果回执 | 绕过外部冲突的写 TXT |
| 扩展自己的术语/偏好 | 有配额的本机配置和命名空间 metadata | 修改其他扩展或宿主的任意私有元数据 |

如果某需求暂未实现，应明确返回 `UnsupportedCapability`，不能让作者通过绕开协议直接改 TXT 来补缺口。对未来未知需求，增加版本化领域 capability；不预设一个 `executeAnything` 兜底。

## 5. 建议 API 面

以下为理想公开接口族，不要求第一版实现所有方法。每个方法的权限、线程、生命周期、输入版本、幂等和失败语义都要写进规范；只列函数名不算完成 API 设计。

### 5.1 会话与读取

| 拟议 API | 返回/作用 | 边界 |
| --- | --- | --- |
| `ctx.project.describe()` | 当前绑定工程的身份、会话 epoch、版本、dirty 状态 | 不枚举其他进程/所有磁盘工程，路径按需授权 |
| `ctx.project.capture(scope, fields)` | 当前时点的新只读快照 | 只在已授权范围内，服务端原子确定版本 |
| `snapshot.pages/labels/groups(...)` | 冻结视图的结构化查询/分页 | 不因用户继续编辑而改变，游标绑定快照 |
| `snapshot.get(ref)` | 同一版本的目标记录 | 目标不在授权中或不存在时明确报错 |
| `ctx.project.changes_since(cursor)` | 有界提交事件及游标 | 不是完整永久日志，过期要求重同步 |
| `ctx.project.subscribe(filter)` | 显式启用的变化通知 | 按事件/范围授权，有限缓冲、可取消、可合并 |
| `ctx.assets.read/materialize/crop(...)` | 版本化图像/裁图素材 | 统一坐标与方向，不是原图任意文件路径代理 |

一次处理要跨页读取时，用同一 snapshot；需要新状态时显式重新 capture。不要提供含义模糊的 `get_current_label()`，让作者在十次调用中读到十个不同的“当前”。

当前选择、页码、视口可通过独立 `ctx.ui.capture_context()` 获取。它们是 UI 上下文，不是工程版本；任务创建时的目标集合固定，用户之后选择别的标签不会将旧任务改指到新目标。确需跟随选择的工具需要单独授权订阅并创建新处理代次。

### 5.2 候选、诊断与图像素材

- `ctx.results.publish(batch)`：发布类型化完整候选；进入宿主草稿，不直接写工程。
- `ctx.diagnostics.publish(set)`：发布带目标、严重程度、定位和可选修正的检查结果；以扩展/检查轮次为作用域替换，不能用追加模式无限重复堆积。
- `ctx.draft.create/update/derive_snapshot(...)`：宿主草稿内组合 OCR、翻译和文本处理；派生快照与真实工程快照类型可区分。
- `ctx.artifacts.create/upload(...)`：提交派生图片或报告等临时产物，限制格式、大小与 MIME；宿主检查后才能预览或导出。不把第三方 HTML 当有任意脚本权限的宿主 UI。

候选不是持久原文的替代品；批准应用时，宿主通过专用 provenance 规则关联原文/译文/素材来源，拒绝插件伪造用户批准或绕过来源隐私选项。

### 5.3 可撤销的领域事务

`proposal = ctx.project.propose(base=snapshot)` 创建的是本地提案 builder，不开启宿主写锁或数据库事务。写集合与必要读依赖由宿主根据操作及 profile 规则验证。

| 类别 | 建议方法 | 关键语义 |
| --- | --- | --- |
| 标签正文/位置 | `labels.set_text`、`set_group`、`set_position` | 完整字段替换、存在性和字段版本前提 |
| 标签增删 | `labels.add`、`delete` | 新增生成新 ID；删除遵守修订/软删除规则 |
| 标签排序 | `labels.move(items, before=anchor)` | 明确 ID 集合、锚点和原顺序版本；不使用 UI 行号 |
| 分组管理 | `groups.add`、`rename`、`move`、`remove(reassign_to=...)` | 去重、关联迁移、默认组约束，移除非空组须指定合法去向 |
| 页面页序 | `pages.move(items, before=anchor)` | 页面 ID 与顺序版本，保持文本/来源/基线关系 |
| 工程内页面成员 | `pages.remove`、`pages.add_from_assets` | 移除不删原图，新增素材须来自批准来源，关联元数据一起规划 |
| 扩展 metadata | `metadata.set/delete(namespace, key, value)` | 仅本扩展命名空间、限量 schema；随文档保存并可撤销 |

标签拆分/合并可作为高层组合操作提供，而不是逼作者拼接模糊的下标修改。需定义来源如何迁移、哪些旧 ID 保留或废弃、新标签如何排序；在这些规则明确前不承诺它们等同于随意 delete/add。创建后继续修改草稿内临时对象可以折叠成最终计划，不能将临时句柄跨无关事务复用。

页面/分组等结构事务是否放入首发 API 可按交付范围裁剪，但架构不应将它们归为永远禁止。危险的是任意写内部容器，而不是领域操作本身。

修订/校对基线、人工配对、审阅状态等若开放，需要对应领域请求；不能通过 `metadata.set("reviewSession", ...)` 越权改宿主数据。自动化来源、稳定 ID 和其他宿主 section 都是保留命名空间。

### 5.4 提交与用户批准

| API | 含义 |
| --- | --- |
| `ctx.proposals.preview(proposal)` | 宿主计算影响、冲突、可审核结构，不调用模型重生成 |
| `ctx.proposals.submit(proposal)` | 保存候选，返回 ProposalRef；没有应用权限 |
| `ctx.proposals.request_apply(ref)` | 请求宿主按策略批准并执行；返回等待句柄/应用回执，不是任意 commit |
| `ctx.proposals.status(ref)` | 查询草稿、拒绝、冲突、应用与保存状态 |

`request_apply` 可以异步等待用户决定，但宿主不能等待脚本释放锁才能显示对话框，脚本也不持有任何工程事务锁。用户批准后仍需再次验证，因为审核期间工程可能变化。

批准策略建议：

| 情形 | 默认批准方式 |
| --- | --- |
| 无副作用检查、候选计算 | 用户启动/启用任务即足够，不弹应用确认 |
| 用户点击已授权的窄范围文本宏 | 用户已明确授权的单次执行许可，可直接应用有效提案并支持撤销 |
| OCR/AI/大范围或结构性修改 | 展示实际候选/影响，用户勾选确认 |
| 后台事件触发 | 默认只生成诊断或草稿，不继承上次点击的单次写许可 |
| 改磁盘文件、覆盖、保存冲突、切换工程 | 专用宿主工作流确认，不能沿用普通标签写许可 |

用户点击宏是否足以免二次确认，取决于**已批准的扩展版本、命令、作用域、操作种类及数量/风险上限**，而非插件声明 `deterministic=true`。超出授权后降为审核或拒绝。权限撤销、扩展更新或 scope 变化都需要重新判断；所有模式始终执行数据完整性校验。

### 5.5 领域工作流与磁盘副作用

采用两段式 `ctx.workflows.plan(kind, request)` / `request_execute(plan_ref)`：

- 保存、另存、导出、页面改名/重新指定来源、建立/结束基线等，调用宿主对应工作流。
- plan 说明是否改正文、metadata、图片文件或工程路径，是否触发保存、清空普通撤销及需要哪些确认。
- execute 在用户批准后再次检查工程与磁盘版本，并返回实际结果，不接受插件提供“用户已批准”的布尔值。
- 输出位置通过宿主选择器发放限域 destination handle；不能将任意路径字符串当成写入授权。
- 不跨网络等待持有文件事务；不把图片重命名混入普通标签内存事务。不同原子性边界分别确认与报告。

这使 API 能支持较完整工作流，但用户仍能区分“已应用到内存”和“已保存到 TXT”，也能识别不能普通撤销的磁盘操作。

### 5.6 UI 与扩展本身的数据

- `ctx.ui.request_form`、`choose_assets`、`choose_destination`、`show_results`、`reveal_target`：由宿主创建标准 UI；worker 只返回结构化数据。
- 自动任务默认不能反复抢焦点；`reveal_target` 只在用户动作或专门授权下执行，翻页/定位走宿主选择协调。
- `ctx.settings.read/update`：本扩展非敏感配置、schema 校验、版本迁移与并发版本检查；不能直接写 `preference.json`。
- `ctx.storage.*`：命名空间内的临时/缓存/持久本机数据，有配额、路径校验和清理策略。
- `ctx.secrets.get`：获得批准逻辑凭据，不枚举密钥环；可扩展宿主 HTTP 代理以避免将密钥交给插件，但不是首版万能网络平台。
- `ctx.task.progress/log/check_cancelled`：任务基础服务，日志有大小限制与脱敏。

**永久不开放的通用逃生口**：QObject/容器指针、任意反射调用、`eval` 宿主代码、直接替换整个工程、清空撤销、无条件覆盖保存、原图任意写入、绕过授权读取密钥。需要新功能时增加有约束的领域 API。

## 6. 持续访问应如何工作

### 6.1 建议三种使用方式共存

| 模式 | 适合 | 工程交互 |
| --- | --- | --- |
| Batch job | 单次 OCR、翻译、格式清理 | 一份输入快照，流式候选，最终一次审核/提交 |
| Interactive session | 先分组再读取结果、分阶段确认的向导 | 同一 worker 多次新快照与有边界的提交；每次得到明确回执 |
| Observer | 边编辑边检查、术语提示 | 有界事件通知 → 新快照 → 诊断；默认不自动写正文 |

它们使用相同快照、提案、批准与错误协议，只是编排不同。长生命周期 session 可以包含多个短 task；不把一个 TaskContext 永远绑定可变的“当前工程”。

### 6.2 多次读取但不产生混合版本

```text
用户工程 R10 -> capture -> 快照 S10 -> 插件计算
用户继续编辑到 R11
插件提交基于 S10 的提案
  -> 依赖未变：可以应用
  -> 依赖已变：冲突，不覆盖
插件需要新状态 -> capture -> 新快照 S11/S12
```

快照本身不可更新；同一遍算法不能一边遍历旧页序，一边逐条读取新正文而不知情。多次 capture 返回不同显式版本，插件需决定重算还是只处理独立未变项。选择某页浏览、拖动分割线等 UI 变化不增加正文版本，也不让任务无故失效。

快照可按需/分页读取并复用素材缓存，不要求每次把全工程 JSON 和整套图像写一遍。实现可从不可变副本与 copy-on-write 起步；不为此先造数据库或完整事件溯源系统。必须有快照生命周期、引用释放、容量上限和 `SnapshotExpired` 错误。

### 6.3 示例：交互式会话

下面是语义示例，不是已经实现的 Python API。函数展示“持续读与受控写”，而不是让作者处理传输。

```python
async def run(session):
    snapshot = await session.project.capture(session.granted_scope)
    proposal = session.project.propose(base=snapshot)

    for label in snapshot.labels:
        proposal.labels.set_text(label, label.text.rstrip(" "))

    ref = await session.proposals.submit(proposal)
    receipt = await session.proposals.request_apply(ref)
    if receipt.outcome != "applied":
        return

    # 新快照，不是让旧 snapshot 变成实时对象。
    current = await session.project.capture(session.granted_scope)
    await session.diagnostics.publish(check_text(current))
```

没有许可时 request_apply 进入宿主审核；有适用的用户单次执行许可时可以直接执行。第二次 capture 读取调用时最新版本，可能包含用户之后的修改，不保证就是 receipt 返回的版本；如果算法要严格处理刚提交后的状态，应请求宿主保留的 receipt 对应快照，过期时明确失败。

### 6.4 事件只提醒，不偷偷复制整个工程

事件最少携带 `documentSession`、提交 revision、受影响 ID/字段类别、origin、cursor。权限范围外的目标与内容不进入事件；正文细节仍由授权快照查询获得。

订阅支持退订、节流、合并、队列上限与 `resync_required`。自动检查拿到更晚版本可以放弃旧结果；诊断按所依据的版本校验，避免把旧错误贴到新正文上。

记录 origin/causation 有助于忽略自身触发，但不足以防止两个插件互相触发。还要限制后台写入、设置触发预算/冷却和用户可见的暂停开关。首版 Observer 只读，不自动沿事件链写工程。

订阅先建立游标再捕获对应版本，或由宿主提供原子的 snapshot+cursor，避免“先读再订阅”之间漏掉变更。事件保留有上限，不能靠日志倒放永久重建工程。

### 6.5 分页应用与取消

默认单次批任务在计算终态后统一审核。确需一边 OCR 后续页面、一边应用已完成页时，使用显式 `segment` 工作流：每段是独立输入版本、审核、事务与回执。

- 应用每段后更新后续阶段的版本依赖；不能继续拿旧的全局下标写后面的页。
- 已应用段进入普通撤销；取消后续计算不撤掉它们，UI 显示“已应用 N 页、未应用 M 页”。
- 用户要求整批一次撤销时，延后整体应用；不要让长期运行任务一直占用一个跨越用户手工编辑的 UndoStack macro。
- 对“全部撤销”提供的应是用户可审查的新回退计划或普通撤销操作，不盲目调用 undo N 次回滚夹在中间的用户编辑。

## 7. 一致性底座：单一写入者与乐观事务

### 7.1 从零设计就应拥有的身份

工程 lineage ID、文档会话 epoch、稳定 page/label/group ID、单调 revision，以及素材身份/内容摘要。ID 解决“是谁”，revision 解决“有没有变”，摘要解决“内容是否符合预期”，三者不能互相冒充。

重命名不改变页面身份，重排不改变标签身份；复制新增对象获得新 ID，撤销恢复原身份。另存可以保留内部 lineage，但不同文件实例/打开会话不能共享无条件可写授权；重载、关闭、恢复和权限撤销使旧 session handle 失效。旧格式导入和 metadata 丢失时需要受控身份重建，不按相同文本猜测旧对象。

revision 在撤销/重做时仍前进，不能退回旧版本号，从而避免“内容恢复原样就误认为期间没有变化”的 ABA 情形。是否允许原值相同但 revision 不同的合并，是宿主明确的冲突策略，不由插件关闭版本检查。

### 7.2 读依赖与写集合

事务包含 base snapshot、写目标及相关前提；宿主掌握实际旧值与版本，插件不能用自行构造的 expectedVersion 冒充授权。

- 修改一条正文至少依赖目标存在、可编辑、正文版本；不必因另一页 marker 移动而失败。
- 删除/合并依赖更完整的目标状态，避免丢掉用户刚写入的新内容。
- 排序依赖页面/标签成员和顺序版本；新增 OCR 标签还需校验输入图片身份及目标页。
- 翻译读取的邻近正文/术语变化影响语义有效性：至少提示上下文已变，默认要求重确认/重算。不能因为写目标没变就声称候选仍然最新。
- 分组移除须验证成员集合，既要处理读到的标签，也要防止随后新增成员形成遗漏。

第一实现可使用较粗的页面/分组集合版本，之后按实际误冲突成本细化字段版本。公开前提语义要从开始明确，但不需要立刻维护每字符版本树或 CRDT。

### 7.3 主线程只做短提交

工程模型由宿主单一所有者修改；在 Qt Widgets 实现中可以先由 GUI 线程持有，并让所有编辑入口共用领域命令服务。计算、网络、解析大消息与素材处理在其他执行上下文进行，不直接碰活动对象。

提交临界区仅执行：检查前提与授权 → 完整应用已规划变更 → 更新 revision/撤销 → 发布模型通知。临界区中不调用插件、不做网络等待、不显示模态框、不主动 `processEvents()`；重型规划可先在快照上完成，提交前再复核版本。

避免两个等待环：GUI 等 worker，而 worker 又同步请求 GUI；GUI 持有工程锁弹确认，而回调又需要同一锁。请求应异步排队，确认发生在事务外。大事务如何保证异常时不留下半批修改，需要由共用编辑服务测试，而不是给每个插件套一层 try/catch。

### 7.4 回执与重复请求

提交回执至少区分 `applied`、`rejected`、`conflict`、`cancelled`、`failed`，并带 commit ID、前后 revision、新对象映射、实际变更计数和 `saved=false/true`。不能仅返回一个容易误解的 success。

同一会话的重复 submit/apply 使用幂等键和提案内容校验；同键不同内容报错。执行状态、候选持久化、内存应用、磁盘保存是不同确认点。

宿主崩溃重启后不要仅凭一次 RPC 超时重放写入；先核实工程状态。尤其不能对收费远端调用或多文件操作承诺 exactly-once。安全恢复可分阶段完善，但未知结果必须显式表示，不能假装失败后随便再执行一次。

## 8. 安全稳定所需的额外边界

1. 任意 Python 代码仍须信任。操作系统沙箱与协议授权是独立层；进程隔离只降低崩溃和依赖耦合，不保证恶意代码不能碰用户文件。
2. 服务端必须验证类型、范围、权限、对象身份和语义，不信任 SDK 已验证。其他语言、旧 SDK 和恶意输出同样要被约束。
3. 网络目的地与密钥绑定；插件更换地址、扩大范围或升级代码不能自动继承全部旧许可。
4. 常驻 worker 设置时间/内存/输出/素材额度；超限停止任务并可重启。单纯消息队列有上限不能限制模型显存，系统级资源管理需另做平台适配。
5. UI 请求可拒绝、可取消、有限频率；后台任务不能用确认弹窗无限轰炸或盗取焦点。
6. host API 不解码任意 pickle，不接受任意对象反序列化，不将扩展返回的路径/命令/HTML 当可执行权限。
7. 领域工作流返回真实错误，不能把忽略操作、部分成功和保存失败包装为同一个“完成”。

## 9. 推荐交付边界

从零实现时，优先级如下，而不是先复制旧 runner：

| 阶段 | 内容 | 不可省略的验收 |
| --- | --- | --- |
| 基础 | 稳定身份、会话/版本、单一命令入口、快照、提案/批准/回执 | 手工编辑与插件操作同样经过规则；冲突不覆盖；一次提交可完整撤销 |
| 可用扩展 | 独立 worker、类型化 SDK、基础标签/分组 API、标准 UI 与测试宿主 | 简单宏不繁琐；OCR/翻译候选无需重算即可应用 |
| 完整编辑能力 | 标签/页序结构事务、受控文件/基线/导出工作流、扩展数据 | 来源/基线/软删除联动；磁盘与普通撤销边界正确 |
| 持续交互 | 新快照、原子 snapshot+cursor、Observer、分段任务 | 编辑中无混合版本；事件丢失可重同步；取消不误回滚 |
| 运维增强 | 离线环境、版本兼容、资源约束、持久候选恢复 | 更新不扰动运行任务；重启不猜配或重复提交 |

一次性快照任务是公开编程模型的简单子集，应长期保留；它不应成为整个平台唯一能做的事情。持续会话是受控组合，不是默认向所有脚本开启任意实时读写。

## 10. 必测场景

- 用户编辑译文时模型返回旧候选；另一页无关修改；文本改动后又撤销为原样。
- 新增、删除、排序、软删除和恢复后，ID、revision、读依赖和撤销行为一致。
- 多次分页读取期间用户重排；选择改变不改变任务目标；重载同一路径不复用旧授权。
- 两插件同时改同字段；一个改正文一个改坐标；组成员在分组移除审核期间改变。
- 用户拒绝、撤销授权、更新扩展、关闭工程时有等待中的 UI/RPC/素材请求。
- 分项发布与取消竞态、重复 apply、丢失回执、宿主提交后重启和候选磁盘满。
- Observer 的事件丢失、双插件互相触发、缓存过期、字幕式高频输入的节流。
- 分段应用后用户手工修改再取消；普通撤销不调用模型也不错误撤掉其他操作。
- OCR 裁图/方向/原图变更，以及导出/重命名工作流失败后不会把内存成功误报成磁盘成功。
- 内嵌/进程外适配若同时存在，必须跑相同契约测试；不能因为实现是“官方可信”就跳过版本与批准规则。

## 11. 最终建议

选择 **进程外、可复用、双向交互的 Python 扩展系统**；工程只通过宿主的 **版本化读取与领域事务** 开放。

不要用一次性文件交换限制产品能力，也不要用内嵌解释器或线程通信绕过一致性边界。API 的完备性来自可组合的领域能力与受控工作流，不来自任意指针、任意脚本赋值或任意文件写入。
