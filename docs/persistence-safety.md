# 持久化安全与失败语义

## 原子文件写入

`core/AtomicFileWriter` 只承担字节写入：检查目标类型，使用禁止直接写入降级的 `QSaveFile`，校验完整写入和 commit 的结果。工程 TXT、报告 HTML、偏好设置共用它，格式序列化仍由各自模块负责。

工程保存失败不能清除 dirty；偏好保存失败不能应用新配置或显示成功。报告临时文件生成成功也必须表示内容完整，不能仅表示文件打开成功。

原子替换解决的是单个文件的可见完整性，不等于对硬件损坏、所有文件系统或多个文件提供断电事务保证。

## 图片改名与工程提交

`ProjectController::renameImages()` 先保存旧工程，再调用 `ProjectImageRenameService`。服务从原工程生成独立候选状态，在文件改名完成后调用工程持久化回调；只有回调成功，才发布候选状态。

文件操作由 `services/io/FileRenameTransaction` 负责：

1. 记录 source / temporary / target 映射。
2. 全部来源先转为同目录的唯一临时文件。
3. 全部临时文件转为目标名。
4. 提交新工程，成功后清理恢复映射。

失败回滚也分两阶段：先把所有已落地目标回收到自己的临时路径，再恢复原始路径。不能直接逐项 target → source，因为来源和目标可能构成链或循环。

如果外部文件占用、权限变化或介质错误阻止回滚，不覆盖外部文件，也不删除尚未恢复的图片；错误应列出失败路径，并保留 `.labelqt-rename-*.json` 映射和临时图片。这些记录是人工恢复线索，当前没有自动恢复中心，不能盲目批量重放映射。工程控制器检测到同目录的未解决记录时，阻止打开和保存；新的改名事务也会拒绝执行，避免按旧状态继续写入。人工核实恢复完成后才能移走该记录；不能直接删除记录绕过保护。

普通失败且回滚成功时，磁盘工程仍是已保存的原状态，内存工程和页面管理草稿不发布新文件名。`ProjectWorkflowController` 只在整个提交成功后清空普通撤销历史。UI 在可能替换项目容器前解除表格等视图的引用，并在成功和失败两条路径都重新绑定和恢复视图。

页面顺序调整仍是独立的普通可撤销工程编辑；不宣称本次改名事务同时自动提交随后进行的页序调整。

## 正文与格式兼容

LabelPlus 结构行只按整行识别。正文中的独立 `-`、`关联文件:`、普通行首尾空白和内部空行不再当作头部信息处理。

经典格式在标签末尾使用空行分隔，无法无歧义地表达正文末尾空行；不同工具还可能规范化 CR/LF。因此 `LabelPlusDocument` 在统一 `LabelQtMetadata` 中维护可选的 `labelText` section，仅为需要保真的标签保存原文与正文 SHA-256。重新打开时，页名、可见标签索引和正文校验都匹配才恢复原文，避免覆盖外部工具修改后的文字。

`labelText` 由当前标签重新生成，不作为 UI 状态；软删除标签不计入可见索引。其他工具移除该私有 metadata 后，仍可读取经典正文，但无法恢复这些原本有歧义的结尾空行/换行编码。

正文若包含独占一行的完整页面或标签结构头，则保存前明确报错，保留旧文件。不要用不透明的文本替换掩盖格式歧义。损坏或不支持的统一 metadata 在工程读写入口明确报错；展示服务仍可通过宽容读取接口得到空结果，避免在 UI 回调中新增未捕获异常。

## 自动化窗口生命周期

异步结束回调建立时就捕获 `QPointer<AutomationRunDialog>`，不能等回调运行后再从原始地址创建 QPointer。运行中的 Esc 和关闭动作只隐藏日志窗口；任务结果应用到工程后才解除编辑锁。窗口隐藏不代表取消脚本，取消仍由明确的取消动作发出。

## 验证

`PersistenceSafetyTests` 独立覆盖原子写入失败、正文往返、元数据保护、链式/循环改名各阶段故障、保存提交失败与异常、回滚受阻时保留证据、dirty/undo 状态和运行中日志窗口 Esc。

测试的重命名函数注入仅位于文件事务边界，不在 UI 中增加测试专用状态。`LabelQtTestSupport` 供现有测试与安全测试复用编译出的核心和服务实现。

本轮不把整个工程宣称为无风险：跨目录另存/备份的图片引用策略、页面移除与 pending 操作协调、完整自动恢复协议仍需后续处理。产品方向见 [产品改进提案](product-design-proposal.md)。
